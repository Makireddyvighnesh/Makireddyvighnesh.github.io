What I learned building an LLM inference engine

October 2026 · Qwen3-4B-Instruct (FP8) on one NVIDIA L4

I could call an inference server, but I couldn't really explain what it was doing. What does time to first token measure, and why does it explode under load? Why does a long prompt make everyone else's stream stutter? What breaks first when requests pile up?

So I built a small engine to find out. The rule I set myself was simple: start from a plain decode loop, add one technique at a time, and measure the exact metric that technique is supposed to fix, with nothing else changing.

1. Measure before you optimize

The first thing I built wasn't an optimization. It was a benchmark harness, a Hugging Face generate() baseline and a manual decode loop, all reporting the same request events. Every number below comes from that harness: one warm-up plus three measured runs, medians, on a single L4 with no memory pressure.

I also checked every engine token for token against Hugging Face generate(). A fast engine that changes the output isn't faster, it's wrong.

2. The KV cache is the first 2×

Without a cache, every new token re-runs the whole prompt. Keeping each layer's keys and values took time per token from 113 ms to 55.9 ms on a 512-token prompt, and the gap grows with prompt length. I gave capacity, positions and release explicit ownership instead of hiding them in library state, which made everything after this easier to reason about.

3. Under load, scheduling matters more than kernels

With static batching, a new request waits for the whole running batch to finish. Serving 16 requests arriving every 150 ms, median time to first token was 9.65 s. Continuous batching admits new requests between decode steps and retires finished ones immediately. That brought it to 0.57 s without touching a single kernel.

Paged KV came next: fixed-size pages with per-request block tables, so the batch can change without copying or re-padding caches. Throughput went from 83.9 to 195 tok/s, and peak memory dropped from 10.8 to 5.6 GiB.

4. Sometimes the GPU is waiting on Python

This surprised me most. Decode was host-bound: about 2,000 kernel launches per token, with the GPU only ~40% busy. Replaying a captured CUDA graph removes the launch overhead. Single-request decode went from 56.1 to 22.6 ms per token, and the GPU went to ~90% busy.

There was a trade-off on the way. Eager paged decode is slightly slower per step than the dense cache (60 vs 56 ms), but it is what makes graph capture possible. In the serving engine I capture one graph per batch-size bucket and pad the live batch to it, so requests can still join and leave between steps.

5. Don't recompute what you've already seen

Chat requests often share a long system prompt. With a prefix cache, identical prefixes share immutable KV pages, tracked with reference counts and evicted LRU. For 8 requests sharing a 2,048-token system prompt, time to first token fell from 1,481 ms to 114 ms.

6. Protect the users who are already streaming

A single 6,144-token prompt processed in one go froze everyone who was decoding for 3.26 s. Mixed batching fixes this: each step holds every decode token plus a chunk of pending prompts, with a cost model choosing chunk size by time. The worst pause dropped to 0.17 s.

The honest finding: on this workload a fixed 512-token chunk budget did just as well. Adaptive sizing only pays off when a long prompt arrives on an idle engine.

What I'd tell myself at the start

  • Pick the metric first. TTFT, time per token, throughput and worst pause each fail for different reasons.
  • Find out where the time goes before writing a kernel. My biggest single-request win came from removing launch overhead, not from faster math.
  • Check correctness on every change. All my scheduling policies produce identical tokens, so speed never cost me the output.
  • Report trade-offs. Paged decode was slower until graphs ran on top of it, and graphs don't help prefill at all.
